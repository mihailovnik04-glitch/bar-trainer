# Барное пособие: PDF-раскладка и тренажёр граммовок

Два продукта из одного источника — Excel-файла с технологическими картами бара:

1. **`build/manual_final.pdf`** — свёрстанное пособие на 72 страницы A4: карточка на каждый напиток
   (фото, состав, украшения, способ приготовления, подача) плюс глава «Система» с закономерностями
   и мнемотехниками.
2. **`build/app/`** — веб-тренажёр на 567 вопросов по граммовкам, украшениям и посуде.
   Работает офлайн, режимы «экзамен» и «тренировка», раздел с ошибками, встроенный **справочник**
   (87 карточек коктейлей целиком + шпаргалки по системе) и всплывающая карточка рецепта
   по кнопке из фидбека и из списка ошибок.

## Железное правило проекта

**Данные из исходника переносятся дословно.** Ни одна граммовка, ни одно название ингредиента,
ни одна строка способа приготовления не переписываются «покрасивее» и не сокращаются.
Пересказывать можно только в главе «Система» — там это авторский текст, а не рецептура.
Скрипт `99_verify.py` проверяет дословность автоматически; он должен проходить перед каждой выдачей файлов.

Если в исходнике встречается очевидная ошибка (например, у «Бабл-ти лимонад · с собой» сумма
жидкостей 150 мл при заявленном выходе 190 мл) — **значение оставляем как есть** и сообщаем
об этом пользователю текстом, а не правкой данных.

## Установка

Сборка идёт из venv внутри проекта — `build.sh` сам его находит и не зависит от `PATH`:

```bash
python -m venv .venv                       # Windows: .venv/Scripts/, Unix: .venv/bin/
.venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python -m playwright install chromium
```

**Windows: все текстовые open() обязаны иметь `encoding='utf-8'`.** По умолчанию там cp1251,
и скрипт молча пишет битую кириллицу в `data/*.json` (мы уже ловили порчу `data.json`).
`build.sh` дополнительно выставляет `PYTHONUTF8=1`. Новые скрипты писать сразу с encoding.

Шрифты (Inter, Manrope, JetBrains Mono, Playfair Display, кириллические сабсеты woff2) лежат в
`fonts/` и вшиваются в HTML в base64 — интернет при сборке не нужен.
Если понадобятся другие начертания: `npm pack @fontsource/<имя>` и распаковать в `fonts/`.

## Сборка

```bash
./build.sh            # обычная пересборка из готовых data/*.json (~40 секунд)
./build.sh --full     # + заново распарсить data/source.xlsx (нужен исходник)
```

Исходного `.xlsx` в репозитории нет — положите его в `data/source.xlsx`, если нужен `--full`.
Всё остальное (разобранные ячейки, якоря картинок, сами картинки) уже лежит в `data/` и `img/`.

## Как устроен исходник (и почему парсер такой)

Excel состоит из 13 листов. Листы с напитками (`Лонг Дринки`, `Шотики`, `Лимонады и БА`,
`Лимонады с собой (Акция)`, `Горячие`, `Самовывоз`) устроены одинаково, но **без объединённых ячеек** —
структура держится только на расположении:

| Колонка | Содержимое |
|---|---|
| A | название напитка — только в первой строке блока (в следующих строках A пустая) |
| B | ингредиент |
| C | граммовка; в последней строке блока — **выход** напитка |
| D | способ приготовления (одна или несколько строк); в строке с выходом — правило подачи |

Отсюда логика `01_parse.py`: новый блок начинается там, где A непустая, а в предыдущей строке A пустая.
Если A непустая две строки подряд — это перенос названия («Малиновый Взвар» + «с ежевикой»,
«Маракуйя-Мандарин» + «Кувшин» + «Безо льда»), части склеиваются через ` / `.

Фотографии привязываются по строке якоря из `images.json`: фото принадлежит блоку, если его
`row` попадает в диапазон строк блока. Колонка > 2 означает дополнительное фото
(альтернативное украшение) — оно кладётся в `extra_photos` и в вёрстке сейчас не используется.

## Формат `drinks2.json`

```jsonc
{
  "sheet": "Лонг Дринки",
  "name": "Сицилийский джин-тоник",
  "total": "180 мл",
  "serve": "Коктейль подается с трубочкой с изгибом",
  "method": "Охлажденный бокал \"Банка\"…",   // дословно, \n между абзацами
  "ing":      [["Джин Босфорд", "40 мл"], …], // всё подряд, как в файле
  "ing_main": [["Джин Босфорд", "40 мл"], …], // без украшений
  "garnish":  [["ПФ Пастила Лимон укр", "1 шт - 2 гр"], …], // где в названии есть «укр»
  "glass": "Банка",          // вычислено регуляркой по method + ручные правки в GLASS_FIX
  "tech": "Билд",            // Билд | Шейк | Стир | Блендер | Питчер
  "straw": "Трубочка с изгибом",
  "formula": [["40", "джин босфорд"], …],     // для строки-формулы в карточке
  "photos": ["media/image41.png"],
  "extra_photos": []
}
```

Разделение на украшения — по подстроке `укр` в названии ингредиента. Это единственный признак
в исходнике, других нет.

### Ловушки распознавания, уже обойдённые

* `tech`: бокал в меню называется **«Шейкер»**, поэтому нельзя искать слово «шейкер» — только
  «шейкерный стакан» / «взбить». Иначе Турбобой, Бомбалейло и Токийский Дрифт станут «шейками», хотя они билды.
* `Бамбл` и `Криспи Айс Латте` упоминают питчер (в нём варят кофе), но это билды — правится через `TECH_FIX`.
* `Рафунтелла` — «взбить» на пароотводе, а не шейкер: тоже `TECH_FIX`.
* Посуда пишется в исходнике по-разному: «Олд фешн» / «Олд Фешн», «Банка с ручкой» с латинской `c`.
  Нормализация — `GLASS_NORM` в `40_bank.py`.
* Варианты «Безо льда» не имеют своего состава (ссылаются на базовый рецепт) — в вёрстке они
  идут компактным блоком `variant_block()` сразу за родительской карточкой, а из тренажёра исключены.

## Что уже проверено на данных (не пересчитывать заново)

* **Выход = сумма всех жидкостей.** Сходится у 84 напитков из 87 с указанным выходом.
  Исключения: `Глинтвейн Алко` (140 → 130, уваривается), `В Питере — пить!` (запись «6*50 мл / 300 мл»),
  `Бабл-ти Лимонад · с собой` (сумма 150 при заявленных 190 — ошибка исходника, оставлена как есть).
* **Цитрусовая лестница украшений:** вейджи убывают по 5 г (апельсин 30 → лимон 25 → лайм 20 → яблоко 15),
  кольцо = вейдж − 5, полкольца = половина кольца.
* **Кувшин лимонада = бокал ×3.** Лимонделло даёт 540 мл, потому что его база 180, а не 200 — правило не нарушено.
* **Суперджус Лимон** встречается в 42 блоках; дозы 10 / 20 / 30 мл (14 / 10 / 10 раз).
  10 мл — в билдах с тоником и содовой, 20–30 — в шейках, блендере и шотах.
* Техники по 98 блокам: Билд 68, Шейк 13, Питчер 12, Блендер 3, Стир 2.

## Вёрстка PDF: грабли Chromium

Печать идёт через `page.pdf()` без полей, поля заданы в CSS. Три вещи, которые ломают вёрстку молча:

1. **Любой элемент шире страницы включает shrink-to-fit** и ужимает весь документ (мы ловили масштаб 0.8
   из-за одной картинки в натуральную величину). Спасает глобальное `img{max-width:100%}` в `style.css` — не удалять.
2. **Отрицательные margin не дают вылезти за margin box**, если PDF печатается с полями. Поэтому
   `@page{margin:0}`, поля — это `padding` у `.sheet`, а обложка получает полноформатную заливку.
3. **Номера страниц через `footerTemplate` требуют полей**, которых у нас нет, поэтому их
   штампует `31_stamp.py` поверх готового PDF шрифтом DejaVu (в built-in шрифтах reportlab нет кириллицы).

Одна и та же `build/index.html` — это и PDF, и экранная версия пособия: `@media screen` даёт липкую
навигацию и поиск, `@media print` их прячет.

## Правки вёрстки пособия

* **Порядок глав, состав главы, цвет главы** — `scripts/config.py`, список `CHAPTERS`.
  Название напитка в `items` должно совпадать с ключом в `drinks2.json` **посимвольно**,
  иначе `assemble.py` падает с «НЕТ НАПИТКА» (это специально).
* **Мнемоники под карточкой** — словарь `MNEMO` там же, ключ — то же имя напитка.
* **Текст главы «Система»** — `pages.py`, обычный HTML внутри f-строк.
* **Справочные главы** — `pages2.py`. Там данные тянутся из `data.json` по номерам строк и колонок,
  поэтому при смене исходника эти номера нужно перепроверять (`sheet_rows()` + `c(row, col)`).
* **Стили** — `style.css`. Карточка напитка: `.card`, состав `.ing`, формула `.formula`, мнемоника `.key`.

## Тренажёр

`quiz_template.html` — самодостаточный файл: стили, разметка и логика внутри, данные подставляются
вместо `__BANK__`. Правки интерфейса делать **в шаблоне**, потом `python3 scripts/41_app.py`.
Не править `build/app/index.html` напрямую — его перезатрёт.

### Справочник внутри приложения

`40_bank.py` собирает `data/recipes.json` из тех же `drinks2.json` + `config.py`, поэтому карточка
в приложении и карточка в PDF всегда совпадают — отдельного источника нет.

```jsonc
{"chapters":[{"id":"sprits","title":"Аперитивы и спритцы","color":"#B33A5B","sub":"…"}],
 "sheets":["Лонг Дринки","Шотики","Лимонады и БА","Лимонады с собой (Акция)","Горячие","Самовывоз"],
 "recipes":[{"name":"Аперол Спритц","ch":"sprits","sh":"Лонг Дринки","si":26,
             "tech":"Билд","glass":"Винный бокал",
             "straw":"Трубочка с изгибом","total":"200 мл",
             "ing":[["Аперитив Аперол","60 мл"],…], "gar":[["Апельсин","25 гр"]],
             "method":"…", "serve":"…", "formula":"60 аперитив аперол + …",
             "key":"мнемоника из MNEMO", "img":"image26",
             "var":[{"name":"… · Безо льда","method":"…"}]}]}
```

Экран «Справочник»: поиск по названию, ингредиенту, украшению и посуде; тап по строке
открывает модалку. **Каждая строка сразу показывает состав с граммовками** (`compHTML()`) —
на телефоне открывать 87 карточек по одной, чтобы увидеть цифры, невозможно; украшения идут
следом и приглушены.

Два порядка показа, переключатель `#refSort`, выбор хранится в `store.refSort`:
* **По системе** — главы пособия из `CHAPTERS`, цвет группы оттуда же;
* **Как в таблице** — порядок исходного Excel. Работает на полях `sh` (лист) и `si` (позиция
  блока в `drinks2.json`) плюс список `sheets` в `recipes.json`. Блоки в `drinks2.json` лежат
  ровно в порядке книги — листы по вкладкам, внутри по строке, — поэтому индекс массива
  и есть «как в Excel»; отдельный номер строки не нужен.

Возвраты (с телефона это было главной жалобой): у карточки коктейля липкая шапка с кнопкой
«‹ Справочник», у экранов справочника и ошибок — своя шапка `.scrhead` с «‹» на главную.
`openRecipe()` кладёт запись в `history`, а `popstate` закрывает модалку, поэтому системная
кнопка «назад» на Android закрывает карточку, а не выкидывает из приложения.

Над списком — свёрнутый в одну строку блок `CHEATS`
(сжатая глава «Система»: правило выхода, техники, трубочки, лестница украшений, лимонадная формула,
шкала доз, шоты, взвары, кофе, чай). `CHEATS` — обычная строка-константа в `quiz_template.html`,
данные в ней **зашиты руками**: при изменении рецептур проверять вручную.

### Структура приложения

Продукт называется **Tokyo-City для сотрудников** и задуман шире барного тренажёра:
направления (бар, кухня, зал), роли (сотрудник, менеджер, директор, владелец)
и категории сотрудников заложены в каркас, хотя работает пока только бар.

Главный экран — три гигараздела (плюс «Роадмап», видимый только владельцу):

| Раздел | Состояние | Что внутри |
|---|---|---|
| **Обучение** | работает | Тренажёр (настройки, «Мои ошибки»), Аттестация (пробная работает, назначенная — заглушка), База знаний, Тренинги (заглушка: календарь и запись) |
| **График** | заглушка | смены по точке: свою видят все, все точки — только директор |
| **Мой профиль** | работает | аккаунт, роль, категория, точка; личная статистика; перенос входа на другое устройство ссылкой |
| **Роадмап** | только владельцу | план развития: что готово, что в работе, что впереди |

База знаний внутри: «Технологические карты» (бывший справочник), «База вопросов»,
плюс заглушки — видео, теория алкоголя, СанПиН → внутренние проверки и РПН.

Отдельные заглушки со своими подразделами: «Статистика» (зарплата, опоздания, часы)
и «Моя карта» (скидочная карта, отметка о приходе). Отметку планируется завести
не своими силами, а связкой с уже готовой внешней системой учёта: QR-код в приложении,
отпечаток пальца или карточка сотрудника.

### График смен: что придётся повторить

Источник — рабочая таблица бара (Google Sheets, лист «график»). Разобрана из CSV-экспорта,
чтобы будущий экран повторял её один в один, но нативно.

* Таблица нарезана на **24 блока по полумесяцам**: строка-заголовок («Октябрь 1»),
  строка дней недели, строка дат, дальше строки сотрудников.
* **15 сотрудников**, у каждого своя строка; в ячейке — смена вида `16-04`, `10-18`
  (встречается и через слэш: `18/04`). Всего 59 разных смен.
* Выходной обозначен крестиком — в таблице соседствуют `x`, `х`, `Х` и `×`,
  то есть латиница, кириллица и знак умножения вперемешку.
* Пометки вместо смены: `квиз`, `генка`, `инвента`, `замена`, `нахим`, `Коменда`
  (работа на другой точке), `др`, `дела`, `до4`, `?`.
* Под блоком — свободные строки-комментарии к дню: «концерт», «Даня нахимова»,
  «до 01 как чт».

Отсюда требования к нативному экрану: сетка «сотрудник × день», ввод смены одним тапом,
нормализованные выходные и пометки (а не четыре вида крестика), комментарии к дню
отдельным полем, подсчёт часов и смен по сотруднику и доступ по роли: свою точку видят все,
сводку по всем точкам — только директор.
Пункт стоит в роадмапе первым, со статусом «в работе».

Заглушки живут в константе `STUBS` в `quiz_template.html`: заголовок, подпись
и список подразделов. Когда раздел будет готов, его карточка меняется на настоящий экран,
а структура доступа уже есть. Полный список запланированного — в константе `ROADMAP`
там же; экран «Роадмап» рисуется из неё и виден только роли `owner`.

**Регистрация временно открыта:** по ссылке на приложение может завести аккаунт кто угодно
(вкладка «Регистрация» на экране входа, подтверждение почты выключено). Новый аккаунт
получает 1-ю категорию и роль `staff`, дальше владелец назначает нужные. В планах —
заменить это пригласительными ссылками; пункт есть в роадмапе.

**Категория и роль назначаются в аккаунте, сотрудник их не выбирает.** Приходят
в `app_metadata` при входе (`category`, `role`, `dept`, `venue`) и лежат в `AUTH`.
Разделы базы знаний раздаются по категории (`KB[].cat` — минимальная категория).
Сейчас у владельца 3-я категория и полный доступ, у 1–2 часть разделов скрыта;
конкретный состав заказчик уточнит позже.

Проставить категорию новому сотруднику:

```bash
curl -X PUT "https://<ref>.supabase.co/auth/v1/admin/users/<uid>" \
  -H "apikey: $SERVICE_KEY" -H "Authorization: Bearer $SERVICE_KEY" \
  -H "Content-Type: application/json" \
  -d '{"app_metadata":{"role":"staff","dept":"bar","category":2,"venue":"название точки"}}'
```

### Экраны и режимы тренажёра

Внутри тренажёра: настройка подбора, «Мои ошибки», «База вопросов».

**Тренажёр** открывается через экран настройки (`renderSetup()`):
* пул — все вопросы / только нерешённые (`store.solved`) / избранное;
* вид напитков — лист исходника (`q.sh`);
* тема — `q.cat`;
* галочка «подсказывать выход».

Дальше `trainPool()` фильтрует банк, выбрасывает напитки из `store.skip` и прогоняет
через `dedupe()` — из-за него в сессии 997 вопросов банка превращаются примерно в 600
неповторяющихся. `dedupe()` дополнительно следит, чтобы «впиши весь состав» и обычные
граммовки того же коктейля не попали в одну сессию.

Ошибка в тренировке возвращается снова через 20–50 вопросов: копия вопроса вставляется
в `S.list` прямо на ходу (один раз на вопрос, флаг `S.again`).

Незаконченная тренировка пишется в `store.sess` на каждом переходе, при `pagehide`
и при уходе приложения в фон, поэтому при возврате экран настройки предлагает
«Продолжить» или «Начать новую».

Кнопка «↶» в шапке — шаг назад к предыдущему вопросу (`prevQ()`, только в тренировке).
Уже отвеченный вопрос показывается с разбором и не пересчитывает статистику (`replay()`).

**Своя цифровая клавиатура** (`padHTML()` / `initPad()` / `padDraw()`): нативная
на телефоне перекрывала карточку и прыгала при фокусе. Пад обслуживает и `num`,
и `fill`, и `mfill` — у последнего несколько полей, переход по кнопке «Дальше»
или тапом по строке таблицы. Физическая клавиатура тоже работает.

**База вопросов** — весь банк списком с ответами, фильтры по виду и теме, звёздочки.
Нужна, чтобы просто посмотреть, что вообще спрашивается, без прохождения теста.

**Мои ошибки** показывает слабые коктейли (сумма промахов по напитку), разбивку
по темам и самые частые промахи, а ниже — полный список.

**Избранное** двухуровневое: коктейль целиком (`store.fav`, звезда в строке справочника
и в карточке) и отдельный вопрос (`store.favQ`, звезда в карточке вопроса и в базе).
Тренировка в режиме «Избранное» берёт и то, и другое (`favQuestion()`).

**Справочник посуды** — третий порядок в переключателе `#refSort`. Собирается
в `40_bank.py` из самих карточек: бокал → трубочка → какие напитки в нём подаются.
Отдельного листа с посудой в исходнике нет.

### Картинки хранятся один раз

Раньше data-URI подставлялся в каждый вопрос, одна картинка дублировалась до 8 раз и `bank.js` весил 3,8 МБ.
Теперь вопрос и рецепт хранят **ключ** (`"image41"`), а сами изображения лежат в `window.IMG` (`media.js`),
460 px, JPEG q70. Итог: `bank.js` 87 КБ, `recipes.js` 81 КБ, `media.js` 1,3 МБ, одиночный `quiz.html` 1,5 МБ.
Функция `src(key)` в шаблоне разворачивает ключ в data-URI — новые места вывода картинок писать через неё.

### Модалка с рецептом

`openRecipe(i)` рисует карточку из `REC.recipes[i]` и показывает нижний лист. Вызывается из трёх мест:
кнопка «Открыть рецепт целиком» в фидбеке после неверного ответа, строка справочника, строка в списке ошибок —
все три несут `data-r` с индексом рецепта, обработчик один, делегированный на `document`.

Важная деталь: пока модалка открыта, вопрос **не должен листаться**. `openRecipe()` гасит таймер
автоперехода, а `onAdvance()` игнорирует тап, если он пришёлся на `#modal` или `#showRec`,
и переподписывается заново. Если будете трогать логику перехода — проверьте этот сценарий:
ошибиться → открыть рецепт → подождать 3 секунды → закрыть → тап должен листать.

### Формат вопроса

```jsonc
{"t":"num",    "cat":"grams",   "drink":"Сила земли", "tag":"", "sh":"Лонг Дринки",
 "q":"Сколько «Тоник ПЭТ 1л»?", "unit":"мл", "a":100, "img":"image43", "r":8,
 "sk":"Сила земли|Тоник ПЭТ 1л|i", "hint":""}
{"t":"choice", "cat":"garnish", "drink":"Улица Роз", "q":"Чем украшается напиток?",
 "opts":["…","…","…","…"], "ai":2, "img":"…"}
{"t":"glass",  "cat":"glass",   "drink":"Кабуки", "q":"В какой посуде подаётся напиток?",
 "opts":[…], "ai":1, "img":""}
{"t":"fill",   "cat":"grams",   "drink":"Сангрия", "q":"Одна граммовка стёрлась. Сколько «Сироп Малина»?",
 "unit":"мл", "a":40, "total":"600 мл", "rows":[["Каберне Макитра (сухое)","300 мл"],…]}
{"t":"mfill",  "cat":"grams",   "drink":"Сангрия", "q":"Впишите все граммовки состава",
 "unit":"мл", "a":[300,40,40,40], "total":"600 мл", "rows":[["ПФ Нарезка на Сангрию","120 гр"],…]}
```

* `cat` — тема: `grams` | `garnish` | `glass` | `method`.
* `t` — способ ответа: `num`, `fill`, `mfill` — ввод числа (у `mfill` полей несколько,
  `a` — массив в порядке пустых строк); `choice` / `glass` — выбор из четырёх.
* `tag` — вид отдачи: «с собой», «на самовывоз · бутылка ПЭТ», «кувшин 1 л», «со льдом»,
  «безо льда». Пустой, если напиток один-единственный. Показывается под названием.
* `sh` — лист исходника, он же «вид напитков» для фильтров.
* `sk` — ключ строки рецепта (`напиток|ингредиент|вид`). По нему тренажёр отсеивает
  повторы: одна и та же граммовка может быть в банке и точным вводом, и выбором,
  и пропуском в составе — в одной сессии берётся только один из них (`dedupKey()`).
* `img` — ключ в `window.IMG`; у вопросов про посуду пустой намеренно.
* `r` — индекс карточки в `window.RECIPES.recipes` (нет у эталонов украшений).

Экзамен набирает 75 вопросов квотами: 46 + 7 по составу, 12 + 5 по украшениям,
3 по посуде, 2 по методу (`pickExam()`); длинные `mfill` (больше 4 полей) в экзамен
не идут. В квоте «ввод числа» лежат `num`, `fill` и `mfill` — при добавлении новых
типов не забыть про `isNum()` там же.

### Требования заказчика к вопросам — соблюдать

* Спрашивать граммовки компонентов, украшения (вес, количество штук, форму нарезки),
  посуду и — редко — метод приготовления. Вопросы про выход напитка, трубочку
  и порядок действий не добавлять.
* **Метод приготовления разрешён с 20.08.2026** (раньше был запрещён), но именно редко:
  один вопрос на каждый пятый напиток, 18 штук на банк.
* Доля вопросов с выбором из четырёх — 40% на строку состава (просьба 19.08.2026).
* Пак «пропущенная граммовка» (`t='fill'`): показан весь состав, одна строка пустая.
  До трёх разных пропусков на напиток. Генерится только там, где выход сходится
  с суммой жидкостей, иначе пропуск не вычисляется, а угадывается.
* Пак «впиши весь состав» (`t='mfill'`): 3–4 строки или весь состав сразу.
  Условие то же — выход должен сходиться.
* Выход напитка в этих паках — подсказка: на экзамене он не показывается никогда,
  в тренировке это галочка в настройках (`store.showTotal`).
* В вопросах с вариантами неверные значения отстоят от верного минимум на 10 и максимум
  на 40, **кроме веса украшений** — там шаг 1–3 грамма (`distractors(..., fine=True)`).
  `99_verify.py` проверяет и то, и другое.
* Посуды — по минимуму (34 вопроса), и только характерная тара: список `GLASS_RARE`.
  Банка и винный бокал намеренно исключены. «Хайбол 620», «Ступенька XL» и «Стакан XL» —
  одна и та же посуда, сводятся к `XL` в `GLASS_NORM`.
* Один продукт может идти и в состав, и на украшение с разными весами (розмарин
  во взваре: 3 гр внутрь, 4 гр сверху). Суммировать нельзя: такие строки спрашиваются
  раздельно с явной оговоркой «не считая украшения» / «ТОЛЬКО на украшение»,
  плюс отдельный вопрос «сколько уходит ВСЕГО».
* Украшения называются с формой нарезки: «Лимон · вейдж». Форма восстанавливается
  по весу с листа «Украшения» (`GAR_FORMS`), а если вес не совпал с эталоном
  и не кратен ему — форма не пишется, ничего не досочиняется.
* Штучные украшения: вопросы про количество штук — только там, где в исходнике есть
  граммы, плюс **бамбуковый лист**. Зонтик, наклейка, пергамент и сахарные картинки
  из вопросов исключены (просьба 20.08.2026) — это сборка подачи, а не рецептура.
* Подсказку вида «указано как 4 шт - 8 гр» у веса украшений не показывать.
* Названия ингредиентов — ровно те же, что в пособии, без сокращений.
* Дистракторы для украшений, посуды, количества штук и форм нарезки берутся из
  **реальных** наборов других напитков, не выдумываются.

### Прогресс и хранение

`localStorage` под ключом `barquiz.v3`:

```jsonc
{"errors":{"id_вопроса": сколько_раз},
 "stats":{"runs":0,"best":0,"right":0,"total":0},
 "fav":{"Аперол Спритц":1},      // избранные коктейли
 "favQ":{"a1b2c3d4e5":1},        // избранные вопросы
 "skip":{"Сангрия":1},           // напитки, убранные из тренировки
 "solved":{"a1b2c3d4e5":1},      // решённое верно — для режима «только нерешённые»
 "sess":{"ids":[…],"k":12,…},    // незаконченная тренировка
 "showTotal":true, "refSort":"ch"}
```

`id` — стабильный, `sha1(sk|drink|cat|t|q)[:10]`, проставляется в `40_bank.py`;
там же проверка на коллизии (при совпадении хешей сборка падает). В `sk` входит строка
рецепта, поэтому три разных пропуска у одного напитка получают разные id.
Миграции: `barquiz.v1` (индексы → id) и `barquiz.v2` (ошибки уже по id) подхватываются
автоматически при первом запуске.

Общей базы результатов нет и пока не планируется: прогресс живёт на устройстве, интернет нужен
только для первой загрузки. Если понадобится отчёт «кто как сдал» — подключать Supabase
(MCP-доступ у пользователя уже есть) отдельным слоем поверх localStorage, не вместо него.

### Известные мелочи UI

* После неверного ответа переход дальше по тапу в любом месте или Enter; слушатель висит на `document`,
  а не на карточке — клик по `disabled` полю ввода событий не даёт.
* Клавиши 1–4 выбирают вариант, Enter отправляет число.
* Тёмная тема жёстко зашита, светлой нет.
* Модалка закрывается тапом по фону, крестика нет — только «шторка» сверху и Esc на клавиатуре.
* Фото в модалке выводится через `object-fit:contain` — коктейли сняты вертикально, `cover` резал бокал.
* PWA есть: `42_pwa.py` кладёт в `build/app` манифест, `sw.js` и иконки, поэтому сайт ставится
  на домашний экран и работает офлайн. Имя кеша содержит хеш содержимого — новая сборка вытесняет
  старый кеш сама. В одиночный `build/quiz.html` PWA-обвязка намеренно не попадает.

## Вход и синхронизация прогресса

Тренажёр закрыт логином и паролем: аккаунты заводит владелец, публичной регистрации нет.
Работает это без библиотеки `supabase-js` — приложение должно открываться офлайн,
поэтому в `quiz_template.html` лежит тонкий клиент поверх REST API (~90 строк):

* `POST /auth/v1/token?grant_type=password` — вход, `grant_type=refresh_token` — продление;
* сессия хранится в `localStorage` под ключом `barquiz.auth`
  (`{token, refresh, uid, mail, exp}`);
* если продлить токен не удалось (нет сети) — работаем на старом, приложение не блокируется.

Адрес и публичный ключ подставляет `41_app.py` из `data/auth.json` вместо маркера `__SB__`:

```jsonc
{"url": "https://<проект>.supabase.co", "key": "sb_publishable_…"}
```

**Пустой `url` = вход выключен**, приложение открывается без пароля. Это сделано специально,
чтобы сборка не ломалась, пока проект не настроен, и чтобы можно было собрать открытую версию.

Прогресс (`store` целиком) синхронизируется через таблицу `public.bar_progress`
(схема и RLS-политики — `supabase/bar_progress.sql`, применяется один раз в SQL Editor).
Отправка — отложенная: `save()` вызывается после каждого ответа, а в базу уходит один
запрос раз в 4 секунды. При входе прогресс не перетирается, а **сливается** (`mergeStore()`):
счётчики ошибок и статистика берутся по большему значению, избранное и выключенные вопросы
объединяются. Иначе вход с телефона стирал бы разбор, сделанный на другом устройстве.

Тесты входа и синхронизации гоняются на поддельном сервере через перехват запросов
Playwright — реальный проект для проверки не нужен.
